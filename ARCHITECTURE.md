# Architecture

How the code is organised and what it is built with. Enforcement lives in `docs/how-to/dev-tooling.md` (`check-architecture`, Biome, token ratchet); the one-line rules are in `CLAUDE.md`. This file gives the reasons.

## Constraints

- Solo developer; Windows + WSL dev box, occasional access to a Mac for builds and signing only.
- Local-only: no backend, no accounts, no sync.
- Habits only. The To-dos and Expenses placeholder tabs were removed in V3 (HAB-26); there is no plan for other modules.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Expo, React Native (New Architecture), React (versions: see `package.json`) | Expo makes iOS development possible without owning a Mac; the New Architecture is the only one left |
| Language | TypeScript, strict | Most code is written by an agent; strict types are what make its output reviewable |
| Navigation | Expo Router (file-based) | A new screen is a new file, not an edit to a central navigator config |
| Database | `expo-sqlite` + Drizzle ORM + `drizzle-kit` migrations | Typed queries, `useLiveQuery` for reactive reads, safe schema changes |
| DB inspection | `expo-drizzle-studio-plugin` | Look at real on-device rows when a streak looks wrong |
| UI state | Zustand (`src/store`, `src/theme`) | SQLite is the source of truth; Zustand holds UI-only state |
| Forms | React Hook Form + Zod | Schemas define the rules once and drive the error text |
| Dates | `date-fns` v4 | Streaks, week boundaries and day-closing are date arithmetic; Temporal is not reliable on Hermes yet |
| Styling | Typed tokens in `src/theme` + `StyleSheet`; custom components | No kit matches the design; tokens are ratcheted (see dev-tooling) |
| Animation / gestures | `react-native-reanimated`, `react-native-worklets`, `react-native-gesture-handler` | Reorderable lists, sheets |
| Native UI / icons | `@expo/ui`, `expo-symbols` (SF Symbols; blank on web) | Platform look |
| Other Expo modules | `expo-notifications` (local reminders), `expo-file-system` + `expo-sharing` (export), `expo-font`, `expo-splash-screen`, `expo-system-ui`, `expo-status-bar`, `expo-linking`; `expo-device` and `expo-constants` are kept for planned diagnostics | |
| Unit / component tests | Jest (`jest-expo`) + React Native Testing Library | Vitest is not reliable for React Native |
| E2E | Maestro (`/e2e`) | YAML flows, little setup |
| Visual regression | Playwright + pixelmatch + pngjs on the web build (`npm run visual-check`) | Fast screenshot diff of every screen state |
| Lint / format | Biome; Husky hooks | One tool, fast enough for every commit |
| Dead code | knip (`npm run deadcode`) | Report only |

Notifications and native modules need a dev-client build, not Expo Go. Nothing here needs a Mac; one only speeds up native builds.

### The `.web.ts` convention

Anything that touches a native API or SQLite has a web twin next to it (`x.ts` + `x.web.ts`) with identical exports. Metro and the web build pick `.web.ts` automatically. The web twins are what let `visual-check` render the whole app in Chromium against in-memory fixtures. A guard test (`_sameShape`) and the `web-twin` architecture rule fail if the exports drift. Every new repository ships a twin.

### Test file naming

Tests are colocated and named after the file they cover: `x.ts` + `x.test.ts`. A variant that exercises one aspect of a file adds a suffix: `x.web.test.ts` (the web twin), `x.live.test.ts` (live-query behaviour), `x.<aspect>.test.ts` (e.g. `category-repository.migration.test.ts`, `habit-lifecycle-service.cycles.test.ts`). Maestro flows in `/e2e` are named by feature ID.

## Layers inside a module

Dependencies point down only: **repositories / strategies / dev ← domain ← services ← presenters ← hooks ← components ← screens** (enforced by `check-architecture`'s `layer-order`).

1. **Repositories** are plain files of exported functions, never classes. They are the only code allowed to import `drizzle-orm`, the db client or the schema (rule 1; this includes `lib/*/repositories/`). They map rows to the module's own `types.ts` types before returning, and they export live-query hooks so nothing above them ever holds a Drizzle query (rule 2; arguments are passed as `useLiveRows` deps). Reason: swapping the data layer then touches `repositories/` only.
2. **Strategies** are one file per frequency type or streak rule, implementing a shared interface (rule 5). Reason: a new frequency is a new file; no tested code is edited.
3. **Dev** (`dev/`) holds the web/visual-check fixtures (`*-fixtures.ts`). It ranks with repositories because the `.web.ts` twins read its fixtures. Reason: dev data stays out of the production layers' folders.
4. **Domain** (`domain/`) holds pure rules: streaks, history, summaries, insights, off-schedule and retro-log rules, export formats. It may use strategies and types but never repositories or `dev/`, so every rule is testable without a database. One accepted exception: `export-json.ts` stamps the file with the app build from `lib/diagnostics/app-info` (static facts, no I/O). Reason: the rules are the app; keep them in one place and side-effect free.
5. **Services** (`services/`) orchestrate: a write that reads first (the freeze pool), several repositories in one action (habit lifecycle, reminders and the OS), or lib adapters (export, the first-run reminder). A single repository call is never wrapped in a service (rule 3). Reason: avoid ceremony.
6. **Presenters** (`presenters/`) turn domain results into what a screen shows: labels, grouping, view models, form schemas. Pure; used by hooks, components and screens. Reason: view logic that several layers share must not live in `screens/`.
7. **Hooks** bridge to screens. `use<X>Queries()` reads, `use<X>Actions()` writes (rule 4). Reason: a screen that only writes should not subscribe to every query.
8. **Components, then screens.** Screens assemble documented components; they never restyle a raw `Pressable`/`View`/`Text` in place of a documented element (rule 10).

Modules never import each other (rule 6). Habits is the only module today, but the rule and its `module-isolation` check stay: they cost nothing, and they keep `lib/` and `components/ui/` free of Habits concepts. A concept a second module would need is promoted deliberately into `lib/` or `components/ui/`.

## Cross-cutting decisions

- **Forms:** React Hook Form + Zod, schemas typed against the module's own types.
- **Dates:** `date-fns` for streaks and week boundaries. Dates are stored as local `yyyy-MM-dd` text, instants as integer seconds. No `86400000` arithmetic, no `Date` maths for weeks.
- **Async writes:** a shared `useAsyncAction(action, { scope, failure })` returns `{ execute, run, isLoading, error }`. `execute` rethrows (for the few callers that show a failure inline themselves); **`run` never rejects** — it logs, shows an error toast (`failure` copy from `failureMessage(verb, noun)`) and resolves `{ ok, value }`, so a caller skips its "it worked" follow-up (an Undo toast, closing a sheet) when `!ok`. Every write hook exposes `run` — except forms that show their own inline error (category add/rename, the habit form, export share/save), which use `execute` or their own try/catch and still log — and every Undo callback runs through `runSafely` in `ToastHost`. A screen with no `ToastHost` above it (the New/Edit habit modals) passes `onFailure` to `runSafely` and shows an inline `Banner tone="error"`. No React Query: there is no server.
- **Messages:** user-facing toasts, banners and inline messages come from the module's catalogue, `modules/habits/messages.ts` (HAB-48; `todayCopy` there holds the inline Today copy: row status lines, group counts, the fold row, sheets and VoiceOver labels): each entry has a `tone`, its `text` (fixed, or built from the habit, date or count it names) and an optional `durationMs` (defaults: Undo 5 s, success/info 4 s, warning 6 s, errors until dismissed). **New copy goes there**, not inline in a screen; existing strings move in as V3 rebuilds each screen (Today's moved in V3-2b). Toasts report events, banners describe states that last; never raw error text (that goes to the log).
- **Logging (`lib/logger`, ADR 008):** `log.debug|info|warn|error(event, fields?)` with a dot-separated `event` (`migration.failure`) and allowlisted `fields`; `fields.error` takes an `Error`. The core redacts before any sink sees an entry (`redact.ts`): a field is kept only if its name is allowlisted (ids and counts as numbers; short lowercase codes in `reason`/`scope`/`kind`…; free-looking text becomes `[redacted]`), and error messages are capped with quoted segments and Drizzle `params:` removed, so never interpolate user text into an `Error` message, use the id. An error object is recorded once however many layers report it. Sinks implement `LogSink` (`write`, optional `flush`) and are registered in `installLogging()`: the dev `ConsoleSink` (the only `console.*` allowed in `src/`, rule `no-console`), a session buffer and `RingBufferSink` (last 500 entries, kept across restarts in its own `logs.db` via `lib/logger/repositories/log-repository.ts` + `.web.ts`, not the habits database). `installGlobalHandlers()` runs first in the root layout, logs uncaught errors and (in release) promise rejections, and always calls React Native's previous handler. "Copy diagnostics" (Settings → About, error screens) builds app version, build, OS, device, schema version, locale, time zone and the recent log, newest last. **To add a sink:** one file in `lib/logger/sinks/` with its test, one `registerSink` line in `install.ts`; no call site changes.
- **Live reads:** repositories read through `useLiveRows(query, deps, options)` (`lib/db`), never `useLiveQuery` directly. It returns `{ data, loaded }`; `loaded` flips true with the first result and **stays true when `deps` change** (week navigation, the day rolling over), keeping the previous rows until the next result so nothing flashes blank. Only a query keyed to one entity passes `resetOnDepsChange`. A query error is logged once and **thrown**, which lands in the root `ErrorBoundary` (`RootErrorBoundary`: "Try again" resets expo-router's boundary, the screens remount and the live queries re-subscribe). Habit lists return `{ habits, loaded }`; screens show a neutral blank (`testID="screen-loading"`) until `loaded`, never an empty state.
- **"Today" and the selected day (HAB-30):** `useToday()` is the real today (updates on returning to the foreground and at local midnight; the same `Date` object all day). The day Today *shows* is `useSelectedDayQueries()` (named `…Queries` for the hook-naming rule), held in `TodayScreen`'s own React state, not a store: `selectedKey` is a past day's key or `null` = follow today. A followed day moves with the midnight rollover (SY5); a past selection stays; future days are not selectable and choosing today clears the selection (`domain/selected-day.ts`). `useTodayQueries(selectedKey)` and `useOffScheduleQueries(day)` key the week window and every per-day read by that day (as live-query deps), and list only habits that had started, weren't paused and were due then (`isHabitListedOn`). Streak-at-risk is computed for the real today only. A write lands on the selected past date, else on `currentDay()` read at the moment of the tap, skipped if the render is a day behind (`useTodayLogActions`); an Undo closure captures the date and what the day held, so it targets the original day however late it is pressed.
- **Today's structure (V3-2b):** `screens/today-screen.tsx` is thin: it reads the hooks, picks the view state (`no-habits` / `rest-day` / `populated`; there is no day-closed state, PR-01 is Later) and renders the header, the `WeekStrip` (`useWeekStripQueries`, data for the *shown* week, which swiping moves away from the selected day's) and one of the sections in `components/today/` (empty state, rest day, habit list = all-done card, progress bar, flat category cards, the dashed fold row). Rows are `HabitRow` (V3-13) over `CompletionCircle` (V3-04), `CountButton`, `IconBadge`; a row's status line is `presenters/today-row-status.ts`. Two tap zones: the **name area opens Detail** (or, on an at-risk row, the streak sheet) and the **circle always logs**. Behaviour lives in action hooks: `useTodayLogActions` (toggle, +1, opening the quantity sheet, rest-day bonus), `useQuantitySheetActions` (the quantity sheet's session), and `useTodayFreezeActions`. The scrolled title is an inline bar the screen draws itself (T5).
- **Sheets (V3-2b):** the **quantity sheet** saves every change at once through `useQuantitySheetActions`: writes are queued so the last one wins, the sheet's day is fixed when it opens, and closing shows one toast whose Undo restores the amount from before it opened (or, if a write returned a frozen day's freeze, says so and puts both back). **Edit this day** (`EditDaySheet`, opened from Habit Detail's heatmap and from Progress; from Progress it has no origin habit, so no note field) lists the habits due that day as `HabitRow`s, saves per tap through `useTodayActions` (a frozen day shows the violet circle; logging it returns the freeze), shows its toast inside the sheet above Done (`Sheet toast="inline"` + `ToastHost placement="inline"`), and keeps the day's note for the habit it was opened from. The note is saved when the sheet closes by `useDayNoteActions`.
- **Toasts (V3-26):** `ToastMessage.tone` is `info | success | warning | error`; `toastHoldMs` decides how long one stays (Undo 5 s, success/info 3 s, warning 6 s, an error until a swipe or Retry). With a screen reader on, a toast is never removed by a timer. `ToastHost` draws the *shown* toast apart from the store's: it fades and rises in over 200 ms, fades out over 200 ms (a 150 ms crossfade under Reduce Motion), a newer toast swaps in at once, and a tap or a downward or sideways swipe dismisses it. `ToastRouteWatcher` (in the tabs layout) dismisses one that has been up more than 600 ms when the route changes; one raised by the navigating action survives. `Sheet` keeps its last content through the Modal's slide-out, and `QuantityLogSheet` waits for it before telling its parent.
- **Freezes and logging a frozen day (HAB-33, PR-11):** the pool is 2 per calendar month shared by every habit, counted by *missed* date (`freezesUsedInMonth`). At-risk does not depend on the pool: with none left the sheet is the one-button SR3 explanation. `services/day-log-service.ts` is the write path for a log that may land on a frozen day: it reads the freeze fresh, and the repository deletes the `frozen_days` row in the same transaction as the entry; `restoreDay` is the Undo and re-inserts the freeze with its original `created_at`. Edit this day saves per tap through `toggleCompletion` / `quantity` writes and `restoreDay` (same freeze-returning path).
- **Transactions:** `runInTransaction` (`lib/db/transaction.ts`) is the one way to write across statements: awaited `begin`/`commit`, serialised so two taps cannot roll each other back. `saveDayLog` and the freeze-aware writes use it; older raw `begin`…`commit` blocks (`habit-repository`) still do their own and should move to it when touched.
- **Startup:** `DatabaseProvider` shows `DatabaseErrorScreen` (Retry, Copy diagnostics, splash hidden) when the file cannot be opened (`lib/db/client.ts` keeps the failure instead of throwing at import) or migrations fail; once ready, `useStartupActions()` reconciles the OS's scheduled reminders against the database exactly once per launch (never prompting for permission, never scheduling anything an enabled reminder doesn't call for).
- **Reminders and the OS (`syncHabitReminders`):** capture the habit's current scheduled identifiers → schedule the new set under a fresh generation (identifiers `"<reminder>:<slot>:<HHmm>:<generation>"` never collide with the old ones) → cancel exactly the captured old identifiers. A failure while scheduling cancels what that run created and leaves the old set; a failed cancel of the old set is logged and left to the reconcile. After a database write has already committed, a scheduling failure is logged but does not fail the action (`syncAfterWrite`).
- **Notifications and file export:** adapters in `lib/` expose this app's own small interface, so the library can be replaced in one file.
- **Progress data layer (V3-3a, `docs/progress-data.md`):** every Progress number comes from one per-day classification. `domain/day-status.ts` answers what a (habit, day) *is* — done, partial, missed, frozen, bonus, not-due, before-start, nothing-logged, future or today — through the habit's FrequencyStrategy (× per week habits are due on open days only); `domain/completion-rate.ts` is the one rate rule (done ÷ due, frozen and bonus left out, today only once done, whole numbers) used by Progress, Monthly, Yearly, Weekly and Habit Detail's 90-day rate; `domain/day-grid.ts` classifies every habit over a run of days once (completions bucketed per habit, no per-day entry scans) and sums per day. On it sit `range-summary.ts` (Week / Month / Year: rate, +N pts, perfect days, best day, ranked per-habit rows, bonus and freezes listed), `progress-grid.ts` (week matrix, month calendar, day detail), `year-map.ts` (level 0–3 for every day, month tiles, best month, the AX month list), `progress-insights.ts` (slipping → improved → nothing to fix, with tone and action) and `progress-unlock.ts` (the 7-logged-days gate and the no-habits / nothing-logged / too-early / ready states). `use-progress-{week,month,year}-queries` and `use-day-detail-queries` read **bounded** ranges (the range plus the one before it, Monday-aligned) with the range, month/year parameter and habit filter as live-query deps; the only unbounded reads are the one-row logged-day aggregate and Week's streak tile. A one-habit variant is the same call with `scopeHabits`. The repository list hooks return memo-stable arrays so the maths can be memoised.

- **Progress UI (V3-3b):** one tab root, `screens/progress-screen.tsx`, replaces the weekly / monthly / yearly screens. It owns the header (`useCollapsingHeader` + `CollapsedHeaderBar`; the Export `HeaderPillButton` runs `ExportSheet`, or toasts `messages.exportNothing` when there is nothing to export), the range switcher (`PinnedBelowBar`: one element that follows the content until it meets the inline bar, then pins) and the sheets (export, habit filter HP1/HP2, Edit this day), and hands each range to `components/progress/progress-{week,month,year}.tsx`, which call their own `useProgress*Queries` and decide between too early / no habits / nothing logged / ready. Which range, the Year chip's habit and the ringed day live in `progress-view-store.ts` (zustand; read through `useProgressViewQueries`, written through `useProgressViewActions`), so they survive a tab switch. A Year month label **pushes** `/month/<yyyy-MM-dd>` (`screens/progress-month-screen.tsx`, a route in the shared Progress stack), so Back and the iOS swipe-back return to Year with its filter and scroll as they were; Month from the range switcher stays in place and is always the current month (D15). Domain output becomes component props in `presenters/progress-presenter.ts` (cells, matrix, tiles, insights, unlock) and `presenters/progress-calendar-presenter.ts` (month calendar, rates, day card, year bands, month list); every word is in `progressCopy` (`messages.ts`). Shared pieces in `components/ui/composite`: `completion-cell` / `completion-legend` / `completion-rows` (V3-05), `week-matrix` (matrix + blocks), `month-calendar`, `year-heat-map`, `month-list`, `mini-month`, `year-strip` (V3-06), `column-chart` + `sparkline` (V3-08), `stat-card`, `chart-card`, `insight-card` + `insight-pager`, `unlock-card`, and the segmented control with its AX collapse. Bars and chart columns share one fill animation (`utils/use-fill-animation`, F-07 "fill", jumps with Reduce Motion). A one-habit Progress (exactly one habit) uses its own variants; Year's chip filters otherwise.
- **Reminders, Settings and Export (V3-4b):** `screens/reminders-screen.tsx` lists `ReminderRow`s (time, own days, `RemoveButton`) and opens one `ReminderSheet` for add and edit, the same sheet the form queues reminders with; `services/reminder-service.ts` rebuilds a habit's notifications on every write (`syncHabitReminders`) and owns the Evening review: `eveningReviewDays` (the weekdays some active habit can be due), `setEveningReview`, `setEveningReviewTime` (stored as `habits.eveningReviewTime`, parsed by `domain/evening-review-time.ts`, default 21:30) and `refreshEveningReview` after a habit changes; the launch reconcile reads the same time. Notification text lives in `notificationCopy`. `screens/settings-screen.tsx` is one scroll of five flat cards over `useSettingsQueries` / `useSettingsActions`. Export is one `ExportSheet` over `useExportStore` (a zustand store: phase confirm, progress, ready or failed; the number of open sheets decides whether a finished export toasts), so closing the sheet leaves the export running; `useExportQueries` reads habits, entries, notes, frozen days, reminders and categories, and `domain/export-json.ts` / `export-csv.ts` write them. Accessibility helper: `useInitialFocus` (`utils/use-initial-focus.ts`) put VoiceOver on a sheet's title, a failed save's error or an export's result.

- **Habits tab and Detail (V3-4a):** `screens/habits-screen.tsx` is the Habits tab root (route `manage`): it owns three bits of UI state (the search query, reorder mode, whether Archived is open) and the collapsing header, and hands the rest to `components/habits/` — `habits-header` (counts eyebrow, gear and +, or Done), `habits-library` (Active header, one `library-group` card per category, or `ReorderableList` in reorder mode), `archived-section`, `habits-search-results`, `categories-row`. `useHabitsQueries` reads the active and archived lists, the running streak of each daily Build habit's row and each archived habit's best streak; `useHabitsActions` is reorder, the VoiceOver Archive and Restore (one toast with Undo; Undo re-archives with the archive date and pauses it had). `presenters/habits-library-presenter.ts` builds row lines, labels and the search (`matchHabits`, accent- and case-folded). Search from the empty result opens Add habit with `?name=`. `screens/habit-detail-screen.tsx` reads `useHabitDetailQueries` (streak, longest, rate and `completionRateDelta`, five `buildHeatmapWeeks` weeks with `before-start` and `isToday`, `habitHistoryRows` — all from the one day classifier) and presents it through `presenters/habit-detail-presenter.ts` (eyebrow, tiles, week rows with one label and one target each, legend, history rows) into `components/detail/`: header, `week-history-card` (rows on `CompletionRows`), history, actions, the archive sheet and the delete sheet over the shared `DestructiveConfirmSheet`. Delete is `runInTransaction` (one transaction; a failure changes nothing) and a failure is the sheet's own banner (`onFailure`), not a toast. Copy is `habitsCopy` and `detailCopy` in `messages.ts`. The paused cell is hatched; `Button variant="compact"` is the 36 pt pill.

- **First run, suggestions and system states (V3-5):** `/first-run` (welcome) and `/first-run/habit` (the New habit form with `firstRun slim`) and `/suggestions` are root-level routes, outside `(tabs)`, so no tab bar is drawn on them. The gate is `(tabs)/_layout.tsx`: `useFirstRunQueries` feeds the pure `firstRunGate` (flag unset and no habits, archived included) and the layout renders `<Redirect href="/first-run" />`; while it is still loading the tabs are drawn. `leaveFirstRun(router)` pops First Run and opens Today; FR3 reaches Today through `first-run-offer-store` (zustand) and `FirstRunReminderOffer`, whose Allow runs `enableFirstHabitReminder` (iOS is asked, then the default reminder is added). Suggestions are data in `suggestions.ts`; `presenters/suggestions-presenter.ts` groups them, derives each subtitle and Added state from the habit list and maps one to a `HabitFormPrefill`. Loading and errors: Today shows `TodaySkeleton` after `motion.skeleton.delay` (`useDelayedFlag`) and is wrapped in `LoadErrorBoundary` (a failed live read stays inside Today). The database gate (`lib/db/database-provider`) takes its words as a `DatabaseCopy` from the root layout (`migrationCopy` in `messages.ts`), so `lib/` stays free of module copy; `planMigrations` reads `__drizzle_migrations` before the migrator to decide whether this launch is an upgrade (SY3, `MigrationScreen`, indeterminate `ProgressBar`) and the migrator itself is untouched (one transaction, so SY4's "Nothing was changed" is true; `migrations.rollback.test.ts` proves it). The midnight rollover is `useToday(clock)` (`lib/today/clock.ts`, injectable) plus `useRolloverQueries` and `TodayRolloverBanner`; the open quantity sheet reads its own day's entry. On web the dev-only `?fixtures=`, `?clock=` and `?textSize=` stay with the page across First Run's redirect.

- **Navigation (HAB-27, ADR 006):** three tabs — Today, Progress, Habits — built as expo-router **shared routes**. The three tabs are *groups* of one stack, `(today,progress,habits)/`, so Detail, Reminders, Settings and Categories are pushed inside whichever tab they were opened from: that tab stays selected and Back returns to its root. Each group picks its root with `unstable_settings` (`anchor: "index"`, `progress: { anchor: "progress" }`, `habits: { anchor: "manage" }`); each tab keeps its own stack across tab switches. Add/Edit habit are root full-screen modals, outside the tabs; everything else short-lived is a sheet.

  The tab bar is `components/ui/composite/tab-bar-pill.tsx`, passed to the navigator's `tabBar` prop. It is absolutely positioned and takes no layout height, so content scrolls under it: every scrolling screen inside the tabs pays `TAB_BAR_BOTTOM_PADDING` (112 pt, T-25) and the shell's single `ToastHost` sits 12 pt above it. At Dynamic Type AX1 and up the pill gives way to the full-width bar A. Sheets are native Modals, so they cover the pill, dim it with the scrim and make it inert (`openSheets`).

  **URLs have no tab prefix** (`/`, `/progress`, `/manage`, `/habit/5`), and a cold link without a group lands on the first tab. Links that must open in a particular tab spell the group out: `/(progress)/progress`. In-app navigation keeps the current group, so `router.push`/`replace` needs no prefix. `src/navigation.test.tsx` guards all of this against the real route tree.

- **Navigation params:** typed routes are enabled; each screen declares its params in its own file.
- **Routes stay thin** (rule 9): a route file changes when addresses change, a screen file when content changes.
- **Reuse before create** (rule 10): search `components/ui/primitives|composite` and the module's components first; reuse, extend, then create (in `components/ui/` first, with every documented state). Colours, shadows, font sizes/weights, spacing and radii come from `src/theme` tokens. New V3 code uses the V3 tokens (`textStyles`, `space`, `radius`, …); existing screens move onto them in the V3 batch that rebuilds them, and the ratchet (ADR 004) counts what is left.
- **Category order:** `categories.sort_order` is the group order on Today and the Habits tab (HAB-42; `groupHabitsByCategory(habits, categories)`, Other always last). The picker and Manage Categories list in creation order (`inCreationOrder`, id order). A new category takes max + 1.
- **Device validation (ADR 007):** a CI-only iOS Simulator build (`.github/workflows/ios-simulator.yml`, manual) opens the visual-check states on a real device runtime. Switched on at bundle time by `EXPO_PUBLIC_DEVICE_VALIDATION=1` (`lib/device-validation/enabled.ts`, not `__DEV__`: the build is Release). Pieces: `dev/device-state.ts` (a scenario's fixtures as plain data, shared with the web repositories' generators via `dev/fixture-search.ts`), `repositories/dev-state-repository.ts` + `.web.ts` twin (replaces the database contents, native only), `services/load-device-state.ts`, `screens/dev-state-screen.tsx` (the `dev-state` route and the launch-request reader, `lib/device-validation/launch-request.ts`) and `lib/dev-clock/shift-clock.ts` (the clock pin web already used). Only that screen may reach the loader; `device-validation.guard.test.ts` enforces it and fails if the flag is set by any other config or the workflow gains an automatic trigger. The driver, Maestro translation and contact sheet are in `scripts/device-validation/`.
- **Starter habits (dev builds only, `docs/how-to/starter-habits.md`):** `StarterProfileGate` (`screens/starter-profile-gate.tsx`) wraps the app inside `DatabaseProvider` and applies the profile in `.env.local` before the first screen, through `services/starter-profile-service.ts` and one transaction in `repositories/starter-profile-repository.ts` (+ `.web.ts` twin). The root layout loads the gate only as `__DEV__ ? require(...)`, so a production bundle has neither the code nor the inlined env value; `check-architecture` rule `starter-profile-site` keeps every other file out. Unlike device validation it is `__DEV__`-based and does not use `dev-state`.
- **Tests:** colocated (rule 8). Reactive-read behaviour is tested against `src/lib/db/test-live-query.ts`, a stand-in for `useLiveQuery`.
- **Migrations:** see the migration guard in `CLAUDE.md` and `.claude/agents/migration-reviewer.md`. A data migration may use window functions, recursive CTEs and a `TEMP` table (0011 does, to hand out rotation slots one at a time without reading rows its own UPDATE changed); test it from rows written in the previous shape (`createPartiallyMigratedTestDb`), with foreign keys on and off. Data rewrites are not reversible; say so in the spec's As-built note.
